## 3. 模型范围与运行配置（冻结）

- **Sol-only**：`AI_MODEL_4` = `gpt-6.1-sol`；一模型承担全部角色、裁决、
  生成、评审、评分。请求与返回模型标识差异照实披露，不冒称已验证身份。
- **配置主线**：既有 `director` + `speech_and_action` 生产配置、标准
  `story_config`（老宅遗嘱）初始场景，无固定样本历史注入；R1/R2 均明确
  使用以下配置，不依赖默认值隐式开启重复干预：

  | 参数 | 冻结值 |
  |---|---|
  | `feedback_enabled` | `true` |
  | `eval_interval` | `2` |
  | `scoring_window` | `8` |
  | `tolerance` | `1` |
  | `repetition_push_enabled` | `true` |
  | `repetition_check_interval` | `3` |
  | `cooldown_turns` | `3`（紧张度与重复干预共享） |

  重复干预路径正是 REP01 推进作用的诊断对象，不能关闭后宣称已验证它。
  这只是显式启用既有配置，不改生产默认值、提示或裁决规则；其他参数沿用
  当前生产配置。冻结、dry-run 与启动检查均验证实际生效配置。
- **运行次数：2 次独立完整运行（R1 → R2）**。同源同配置，仅运行目录
  不同；不共享状态。两次可观察障碍是否在两条轨迹中重复出现；单次也能
  提供具体反例或合法完成轨迹，但两次**不足以判明偶然性或建立可靠性**。
  报告必须如实声明该限制；不将两次诊断当作受控因果比较。
- **源冻结**：实施前固化 dirty worktree 与实际触碰文件；运行共用一份
  字节相同的源快照；不为提高完成率修改任何生产源、提示、解析或模型
  参数。

## 4. 预算（冻结）

| 项 | 值 | 说明 |
|---|---|---|
| `total_turn_limit` | 24 / 每次 | 与控制轮一致（实际最多用 20） |
| `total_model_attempt_limit` | 400 / 每次 | 每次运行独立预算；不跨运行结转、不重分配 |
| SDK `chat.completions.create` 硬上限 | 400 / 每次 | runner 在转发每次 SDK 调用前预扣；含选择题重问与外层重试引发的每次调用 |
| 历史用量参考 | 154 Concordia attempts | 控制轮最大观测值，不是新运行的预计用量或停止阈值 |

R1/R2 合计最多 800 Concordia attempts、800 次 SDK `create`；两套额度
分别核算，任一耗尽即停止该运行。SDK `max_retries=2` 保持生产值：按
每次 SDK 调用最多三次 HTTP 尝试推导，每运行重试尝试上界为 1200，
两运行合计 2400。此为 SDK 重试配置推导的上界，不是实测 HTTP 请求数、
提供方计费认证或目标用量；SDK 次数也不等于 token 或金额预算。

**口径披露（分别列报，不混为一数）：**

- 400 计 **Concordia 层 model attempts**（生产 `BudgetGuardLanguageModel`
  守卫不变）：每次穿过该 guard 的 `sample_text` 或 `sample_choice`
  尝试预扣一次。外层 API 重试重新经过 guard 并计数；一次选择题尝试内
  的多次 SDK 请求不据此假定为多个 Concordia attempts。
- SDK 默认 `max_retries=2` 在计数层之下，HTTP 请求数可超过计数；
  外层 tenacity **最多 3 次尝试（最多 2 次重试）**，仅重试
  `APIConnectionError` / `APITimeoutError` / `RateLimitError`，固定延迟
  `0.0`、jitter `(0.0, 0.0)`、`exponential_backoff=false`。
  依据 `run.py:build_simulation` 与 `retry_stats_wrapper.py`，不能把
  通用 retry wrapper 的默认指数退避误写成此链路的实际行为。
- 保持生产重试与选择题解析/重问行为，直至本协议的预算停止边界；不得
  复制 S2 的 `max_retries=0` 或一个逻辑 slot 只准一次 SDK 调用的守卫。
  SDK `create` 必须逐次记账；若未在 HTTP 发送边界逐笔观测，报告的
  `http_requests_observed` 标为未观测，另列上述推导上界，不填 SDK 次数。
- **账本纪律**：Concordia attempts 与 SDK requests 两类计数分别由
  追加式账本的对应 started 重建，记录关联但不混加、不互相代替。
  每层均在向下调用前持久化 started 预扣，finished 不再次扣费，失败与
  未决不退款；不从 summary 缓存或手写值恢复消费。预算审计、旁侧证据、
  源/协议哈希异常均在下一次转发前停止，不能猜测补零。
  并发调用使用独立标识，预扣与上限检查须同步，不能依赖全局 active slot。
- 最小账本化 runner 复用生产 `run.py`、已有模型包装、请求账本与归档
  工具；不重建故事循环、不新增语义评审或额外模型调用。SDK 额度停止
  属实验边界，应另列停止层与实际消费，不能冒称 Concordia 400 已耗尽。
  它是执行前置交付物，随实施计划另立，需通过零网络 dry-run。

## 5. 失败处理（冻结）

| 情形 | 处理 |
|---|---|
| 语义评审拒绝 | 生产停止行为（`StoryOutputError` → reason=error，不重新生成）；该运行结束，批次按 R1→R2 继续 |
| 认证 / 路由 / 启动器失败 | 非零退出即停止批次，保留现场，记录未启动运行；退出码不掩盖 |
| Concordia / SDK 任一预算耗尽、beat_timeout | 记录实际停止原因与层次；无基础设施故障时按注册顺序继续下一运行，额度不结转；**beat_timeout 不是完成结局** |
| 运行中断 | 本轮默认停止该运行并暂停批次、保留现场，标为 interrupted，交用户审阅；不自动 resume、跳过 pending、补跑、替换样本或生成缺失结果 |
| 禁止 | 改提示、结局条件、裁决规则或预算来提高完成率；no auto-repair、no best-of、已完成运行不重跑 |

本 runner 不要求实现进程中断恢复。S2 的独立样本跳过规则不能直接用于
故事的未提交回合：记账正确不代表故事状态可继续。后续若另行设计恢复，
须核对 checkpoint、已提交事件、全部消费、未提交回合及过程归档，遵守
生产对预算耗尽和缺失过程记录的拒绝条件，明确已完成请求如何避免重发，
并先做确定性验证、取得单独授权；不得改账本、伪造 summary 或填入模型
结果绕过校验。即使仅继续未启动的 R2，也需中断原因审阅后授权。

## 6. 逐轮评价标准（冻结）

每次运行逐轮记录五问（逐轮、可引用原文证据）：

1. **回应具体性**：角色是否回应本轮具体问题与具体他人话语，还是
   程序性重复？
2. **条件满足后的行动**：条件满足时角色是否行动或明确拒绝（含不同意、
   换策略）；各角色声音是否可区分？
3. **世界回应的因果**：上一轮结果（成功/失败/阻塞、新信息）是否改变
   下一选择；新信息是否有来源、是否只到达被允许的听众？
4. **实际推进判定**：首次发现阻塞若改变角色掌握的信息、可行选择或
   具体策略，可以计为推进，不自动计分。记录、照明、核验、协商等必要
   步骤若改变可行动条件或落实具体安排，同样可能是进展；不得按动作名称
   一律排除。重复准备、改述请求、无依据的额外核验以及没有实质变化的
   微步不算推进；对照 G4 turns 11–18 时，逐项引用实际变化或缺乏变化
   的证据，不能仅因出现新文字而记为进展。
5. **导演效果**：干预是否减少循环、改变局势，还是仅插入事件？

**汇总诊断指标：**

- 循环段识别与计数；推进/循环事件比。
- 干预-循环因果记录（对照设计 §2.2：仅敲门发生 ≠ 停滞改善）。
  分开记录重复干预的检查机会、实际执行、合法提交，以及随后选择/循环
  的变化；启用开关不等于必定触发，无适用机会或无实际执行时标为未覆盖，
  不强制敲门、生成回应或增加干预来补齐样本。
- **结局条件核对表**：四个允许结局（真相大白 / 秘密永埋 / 协商保宅 /
  僵局散场）逐项列出各自条件是否真实发生；进入终局节拍 b4 不足为凭
  （控制轮教训：G4 入 b4 而保险柜从未打开）。
- 评审误拒嫌疑记录：REV05/REV07 型边界行为被拒的条目单列，不自动
  计为模型违规。
- 合理超时照实报告，不粉饰为接近完成。

## 7. 结论语义与产出

- 诊断报告只回答「障碍在哪」：逐轮五问、循环诊断、结局条件核对、
  误拒嫌疑。**不宣布 MVP 质量验收**。
- 若出现至少一条完整合法结局轨迹，仅记为「完成轨迹已演示」；两次
  运行不确立可靠性。
- 每次运行产出生产产物（`run_manifest.json`、`summary.json`、
  `story_turns.jsonl`、checkpoint、script）+ 请求账本；批次级产出
  逐轮评价记录与 README（引用证据、口径披露、未证明清单）。剧本
  导出（FDX/Fountain）随产物保留，不作为本轮诊断门。
- 分列 Concordia attempts、外层 API retries、SDK `create`、已观测
  响应、未决与 HTTP 是否实测；将原生产 summary 与账本重建值交叉核对，
  不覆盖原始数据来消除差异。附上源快照/配置哈希与旧控制轮的依赖差异，
  旧轨迹仅为历史参照，不宣称两批差异由单一修复造成。

## 8. 停止边界

执行前须依次满足：本协议审阅修正回填 → runner 实施计划与零网络工程
交付 → 工程审阅通过 → 用户单独授权真实执行（届时在 `run_results` 下
新建冻结批次目录）。本协议本身不发起任何调用，也不因回填而自动授权
最多 800 次 SDK 调用及其生产重试。

## 已回填的运行规模与边界

| 项 | 待冻结值 | 边界 |
|---|---|---|
| 运行次数 | 2（R1→R2） | 不增加第三次、不重跑已结束运行 |
| turn 上限 | 24 / 次 | 总上限，不要求用满 |
| Concordia attempt 预算 | 400 / 次 | R1/R2 独立，生产重试仍经过 guard |
| SDK `create` 预算 | 400 / 次 | 单独预扣和硬停止；合计最多 800 |
| HTTP 请求尝试上界 | 1200 / 次 | 按 SDK max_retries=2 推导；无逐笔观测则不当作实测数 |
| 重复干预 | 显式启用 | interval=3、共享 cooldown=3，不保证实际发生 |
| 账本化 runner | 执行前置必需 | 先实施、测试、dry-run、审阅，再授权真实执行 |
| 中断 | 停止该运行并暂停批次 | 恢复或继续下一运行另行审阅授权 |

## 9. 给工程师的下一步指令（零真实调用）

1. 阅读本文、S2 设计 §4/§9、AGENTS.md，以及现有 `run.py`、
   `request_ledger.py`、`budget_wrapper.py`、`retry_stats_wrapper.py`、
   `provenance.py` 和相关测试。固化当前工作区与实际触碰文件，保留旧批次。
2. 先将最小 runner 的实施步骤写入
   `docs/superpowers/plans/2026-10-23-sol-s3-diagnostic-runner.md`，明确
   文件范围、包装层位置、双层计数及关联、并发预扣、原始请求/响应留证、
   停止规则、测试与 CLI。计划停在审阅点；不要把编写计划当成实施或调用
   授权。复用已有包装与生产入口，避免复制 S2 的禁止重试逻辑。
3. 计划审阅通过后实施 runner 与 colocated 确定性测试；不改故事提示、
   角色规则、结局条件、生产默认重试，不新增模型调用。默认不支持 resume。
   实施可以在临时目录验证 freeze，但不在 run_results 冻结真实批次。
4. 必测边界：两次运行隔离且生效配置相同；重复干预明确开启；
   Concordia 与 SDK 次数不同仍能分别正确计数；选择题重问及生产 API
   重试保留；每层额度满时下层零新增转发；并发不超支；缺失/漂移/重复
   账本与旁侧记录拒绝；中断不重发、不中途恢复；预期语义拒绝结束该运行
   后按协议进入下一次；认证/路由/启动器故障暂停批次。
5. 全部 CI 测试使用 MockModel 或同类确定性假客户端。dry-run 不读凭据、
   不建真实客户端、无网络，检查双运行计划与实际配置、提示、归档、预算
   和失败分类；模拟触发重复干预只证明接线，不声称真实推进效果已验证。
6. 运行受影响测试及仓库要求的 pytest/lint/type/format 检查；分列既有
   问题。交付实施 diff、测试结果、dry-run 目录和实际可执行的 freeze/run/
   summarize 命令，**停在工程审阅点，不 commit、不清理、不调用真实模型**。
7. 工程审阅通过且用户另行明确授权后，才在新批次冻结源码、配置、协议与
   预算，顺序执行 R1/R2。逐运行核验哈希，保留全部失败，不补跑；最终
   离线汇总并按 §6 逐轮评价，停在结果审阅点。

当前仓库尚无该 S3 runner，本文件不提供虚构的启动命令。工程师完成前置
交付后，应使用其经验证的 CLI；不能直接运行旧 `run.py` 绕过 SDK 账本上限。

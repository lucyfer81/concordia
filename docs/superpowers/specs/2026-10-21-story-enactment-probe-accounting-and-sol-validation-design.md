## 4. S1：统一请求账本、预算和恢复

### 4.1 唯一计数来源

未来 runner 的预算、恢复、报告统一从追加式请求账本重建，report.json
仅为派生视图。禁止从上次 attempt 结束时的 report 计数恢复，也禁止
在恢复脚本中手写每模型、每组或每样本已用数量。

每条记录包含 batch_id、attempt_id、slot_id、模型、组、样本、调用阶段、
事件类型、时间与相关输入哈希。批次内 slot 唯一；新批次独立计数。

1. 请求前检查所有预算，再持久化 started 预扣记录，成功后才允许调用 SDK。
2. started 一经持久化即占一个预算额度，包括 API 错误、超时及无结果。
3. finished 记录终态，不再增加预算。不能只在 finish_slot 中累计消耗。
4. frozen_stub、正常无需执行的后续分支、skipped 和第二请求被阻止均不
   新增额度；被阻止前已经发出的第一次请求仍计一次。
5. 状态与消费按记录的模型/组/样本重建，不依赖当前 active model 等易失变量。

started 与 finished 区分预算预扣和响应观测。崩溃可能发生在落盘与实际
发送之间，无法证明是否发送时记为“已占额度、发送/结果未决”，不退款，
也不冒称拿到了提供方响应。无需引入数据库或通用事务框架。

账本作为权威记录应采用完整 JSONL 记录写入并落实持久化；旁侧 started
文件、请求正文和报告与之交叉检查。发现截断尾行、孤立 started 标记、
重复 started、同 slot 模型不一致或 finished 无 started 时，列为审计
异常并拒绝继续付费请求，不静默丢行或重新发出请求。

### 4.2 请求与响应的留证时机

- 请求前保存实际提示与参数，不能等调用返回后才保存。
- 在 SDK 观察边界、解析之前保存原始响应和返回模型标识；选择题解析
  失败也必须有首次响应，不只保存异常文本。
- SDK 实际提交的 messages 与上层提示如有追加内容，应记录可审计的
  对应关系或脱敏后的完整请求；不能把上层提示误称为全部实际请求。
- 不改变实际生产提示、样本、模型参数；凭据及认证头不进入任何产物。

这不能保证 SIGKILL 前所有内存内容均已保存；无法保存的部分如实标未决。

### 4.3 恢复规则

重入前重建所有计数并检查源文件/协议哈希、slot 唯一性和未决项。
正常协议继续禁止自动重发 started_no_result。若用户明确批准跳过某个
未决样本后继续，只放开该项停止条件，仍预扣全部 started，保留偏差原文
及其范围。授权不推导为其他失败可重试或额外预算。

本批已有原始 started/finished 文件和日志足以重建 82 次口径，不需要
修改旧恢复脚本或再运行它来“证明”修复。

核对全部所需条目，不能仅用“当前存在的标签全部是 human”判定完整。

## 7. G：Gemini 选择题格式兼容的独立设计

当前主线不依赖此项完成。后续若实施，修改范围应限于 OpenAI 兼容适配器
的 sample_choice 解析及 colocated tests，不修改 InteractiveDocument、
核心裁决、角色输出、语义评审 schema 或本批冻结探针。

先做已有响应的离线验证，再决定是否进入生产补丁。建议采用如下窄规则：

1. 优先沿用 answer 与 responses 的原始精确匹配，合法的完整文本选项
   不受影响，避免把本来合法的“b.”文本选项错误解释成字母。
2. 仅当 responses 非空、全部是互异的单个 ASCII 字母时，才启用格式兼容。
3. 在该条件下，去除首尾空白后，允许一个合法选项字母，以及其后可选
   的一个英文句点或右圆括号。例如 b、b.、b)；保持原大小写。
4. 必须完整匹配整段答复。多选、解释性文字、未知字母、重复标点、
   Yes/No 词语与其他字符串不由本规则转换；不截取第一个字母猜答案。
5. 用规范化后的合法字母查 responses 得到 index，再由现有文档层映射
   选项含义。b 在 REP01 为 Yes、在 REP02 为 No，不能直接编码其语义。
6. 原始响应留档；返回选择和诊断分别记录原始值、规范值与是否应用兼容。
   格式兼容不新增请求，不自动扩大重试次数，不修改原批次失败判定。

无网络测试覆盖两条已观测答复、纯字母精确匹配、所有允许的空白/单标点
形式；在 responses 为 a/b 时，验证 a or b、b because…、z、b..、b.)、
空串等均被拒绝；还需验证
多字符/本来含标点的合法选项维持精确匹配优先。确认首答成功时没有第二
次提供方请求，失败仍走既有策略和实验单 slot 守卫。

不能只在探针做兼容后宣称生产已修复。若修改共享适配器，需单独评估对
其他调用方的影响，并运行 provider、document 及相关回归。原样本的
离线可解释性不等于已经验证修改后的生产链，后续真实复验另立协议。

REP01 的实际推进作用仍待验证。若它尚未获得质量确认，完整故事首跑应
明确定位为“诊断故事发展”的实验，而非宣称所有固定样本质量门槛已通过
后的最终验收。预先写明这种研究范围调整，再获得相应执行授权。

后续建议使用既有 director + speech_and_action 配置、当前故事与时限
预算作主线，固定运行次数与失败处理。Concordia attempts 和实际 SDK
请求口径、生产重试策略分别披露。本设计不冻结或发起该批运行。

逐轮评价角色是否回应具体问题、条件满足后是否行动或明确拒绝、世界回应
是否影响下一选择、导演是否减少循环，以及允许结局的全部条件是否真实
成立。合理超时照实报告。只有新的完整轨迹显示具体障碍，才设计针对性的
故事机制修补；不因固定样本结果不齐而继续扩大故事架构。

准备，不包含付费调用、故事生产提示改动或历史产物覆写。

故事/私密功能的未证明事项，并停在审阅点。
